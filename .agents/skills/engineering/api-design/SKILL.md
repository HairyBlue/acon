# API Design Standards

High-performance, durable distributed systems depend on predictable, well-specified API contracts. This skill defines architectural standards and concrete implementation patterns for HTTP REST APIs, error envelopes, idempotency, pagination, and webhook integration.

---

## 1. Resource Modeling & HTTP Semantics

### URI Structure & Resource Collections
- **Use plural nouns for resource collections:**
  - Good: `/api/v1/orders`, `/api/v1/customers`, `/api/v1/subscriptions`
  - Bad: `/api/v1/order`, `/api/v1/getCustomer`, `/api/v1/new-subscription`
- **Use kebab-case for multi-word paths:**
  - Good: `/api/v1/payment-methods`, `/api/v1/shipping-addresses`
  - Bad: `/api/v1/payment_methods`, `/api/v1/paymentMethods`
- **Model relationships through hierarchy (limit depth to 2 levels):**
  - Sub-resources: `/api/v1/orders/{order_id}/items`
  - Deep nesting anti-pattern: Avoid `/api/v1/organizations/{org_id}/teams/{team_id}/projects/{project_id}/tasks/{task_id}`. Flatten once an entity possesses its own unique identifier: `/api/v1/tasks/{task_id}`.
- **RPC-Style Sub-actions (Controller Verbs):**
  When a business operation does not cleanly map to standard CRUD mutations, model it as a sub-resource verb:
  - `POST /api/v1/orders/{id}/cancel`
  - `POST /api/v1/invoices/{id}/void`
  - `POST /api/v1/checkout/process`

### HTTP Verb Semantics

| Method | Safe | Idempotent | Usage |
|---|---|---|---|
| `GET` | Yes | Yes | Retrieve resource or collection representation. Never mutate server state. |
| `POST` | No | No* | Create a child resource or execute an imperative command. (*Idempotent when paired with `Idempotency-Key`). |
| `PUT` | No | Yes | Full replacement of target resource. Requires sending full representation. |
| `PATCH` | No | Yes* | Partial modification of target resource (e.g. JSON Merge Patch RFC 7396). |
| `DELETE` | No | Yes | Remove the specified resource. Subsequent calls return `204` or `404`. |

### HTTP Status Code Authority Matrix

Never invent custom codes. Always map server results to standard HTTP status codes:

- **`200 OK`**: Standard success response for `GET`, `PUT`, `PATCH`, or non-creation `POST` actions returning data.
- **`201 Created`**: Successful `POST` resulting in a new resource. **MUST** include the `Location: /api/v1/resources/{id}` header pointing to the newly created resource.
- **`204 No Content`**: Action succeeded and the response body is intentionally empty (standard for `DELETE` and state-toggle mutations).
- **`400 Bad Request`**: Malformed request syntax, unparseable JSON payload, or invalid query parameters that prevent server parsing.
- **`401 Unauthorized`**: Authentication is missing, expired, or invalid. (Must include `WWW-Authenticate` header).
- **`403 Forbidden`**: Caller is authenticated, but lacks sufficient permissions (RBAC/ABAC violation).
- **`404 Not Found`**: The requested resource URI does not exist.
- **`409 Conflict`**: Request cannot be completed due to conflict with current system state (e.g., duplicate unique key, state machine violation like transitioning an already cancelled order, or concurrent modification).
- **`422 Unprocessable Content`**: The request payload syntax is well-formed JSON, but contains semantic/domain validation errors (e.g. invalid date order, field values out of range).
- **`429 Too Many Requests`**: Client has exceeded rate limits. **MUST** include `Retry-After: <seconds>` header.
- **`500 Internal Server Error`**: An unhandled server-side failure occurred. Never leak raw stack traces or database error strings to the client.

### The Cardinal Rule: Forbid 200 OK Error Payloads
> **NEVER return `200 OK` with an error payload (e.g. `{"success": false, "error": "Unauthorized"}`).**

Returning `200 OK` for failures breaks:
1. Reverse proxies, CDNs, and edge caches (which cache 200 responses).
2. Standard HTTP client libraries, interceptors, and retry middleware.
3. Observability, metrics aggregators, and APM error-rate alerting.

## 2. Standardized Error Responses: RFC 7807 (Problem Details)

All error responses (`4xx` and `5xx`) **MUST** format their response body using **RFC 7807 (Problem Details for HTTP APIs)** and specify `Content-Type: application/problem+json`.

### Canonical Fields
- `type` (string URI): A URI reference that identifies the specific problem type (serves as documentation reference).
- `title` (string): A short, human-readable summary of the problem type (should not change from occurrence to occurrence).
- `status` (integer): The HTTP status code generated by the origin server.
- `detail` (string): A human-readable explanation specific to this occurrence.
- `instance` (string URI): A URI reference identifying the specific occurrence of the problem (e.g., request trace ID).
- `invalid_params` (array, optional): Extension member for validation failures, detailing each invalid attribute.

### Example 1: Domain State Conflict (`409 Conflict`)
```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/order-already-shipped",
  "title": "Order Cannot Be Cancelled",
  "status": 409,
  "detail": "Order ord_891723 cannot be cancelled because shipment pkg_4492 has already departed.",
  "instance": "/api/v1/orders/ord_891723/cancel"
}
```

### Example 2: Granular Validation Errors (`422 Unprocessable Content`)
```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Validation Failed",
  "status": 422,
  "detail": "The payload failed 2 validation rules.",
  "instance": "/api/v1/subscriptions",
  "invalid_params": [
    {
      "name": "billing_cycle",
      "reason": "Must be one of ['monthly', 'annual']",
      "code": "value_not_allowed"
    },
    {
      "name": "seats",
      "reason": "Minimum seat count for enterprise plan is 10",
      "code": "below_minimum"
    }
  ]
}
```

## 3. Idempotency Key Mechanics

Network requests can fail due to dropped packets, timeouts, or client disconnections. Without idempotency, client retries cause duplicate payments, double orders, or repeated side effects.

### Header Specification
```http
Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
```
- Supported on all mutating endpoints: `POST`, `PATCH`, and custom RPC sub-actions.
- Value: Unique client-generated token (UUIDv4 recommended; max length 255 chars).

### Fingerprinting & Request Binding
To prevent malicious or buggy key reuse across different operations, the server computes a **Request Fingerprint**:
```
fingerprint = SHA256(client_id + ":" + http_method + ":" + path + ":" + raw_request_body)
```

### Execution Lifecycle

```
Client sends request with Idempotency-Key
                  │
                  ▼
         [Check Key in Store]
         ┌────────┴────────┐
         │                 │
     [Key Found]      [Key Not Found]
         │                 │
   Check Status            ▼
   ┌─────┴─────┐      Acquire Distributed Lock (TTL 60s)
   │           │      Record state: IN_PROGRESS
[IN_PROGRESS] [COMPLETED]  │
   │           │      Execute business transaction
   ▼           ▼           │
Return 409   Compare Hash  Save response (code, headers, body)
Conflict     ┌─────┴─────┐ Store TTL: 24-72 hours
             │           │ Release Lock
         [Mismatch]    [Match]
             │           │
             ▼           ▼
         Return 422   Return Cached Response
         Payload      Header: `Idempotent-Replayed: true`
         Mismatch
```

1. **New Request:**
   - Attempt to acquire distributed lock (e.g. Redis `SET key lock NX EX 60`).
   - Store record with status `IN_PROGRESS` and request `fingerprint`.
   - Execute database transaction and business logic.
   - Atomically persist response status code, headers, and body with a 24-72 hour TTL.
   - Release lock and return HTTP response.
2. **Concurrent In-Flight Request:**
   - If a second request arrives with the same key while the first is still `IN_PROGRESS`:
   - Return `409 Conflict` with `Retry-After: 2` (or wait on condition variable up to 2 seconds).
3. **Completed Key Replay:**
   - If the key exists with `COMPLETED`:
   - Check current request fingerprint against stored fingerprint.
   - If **mismatch**: Return `422 Unprocessable Content` (Error: *Idempotency key reused with different payload*).
   - If **match**: Return the cached response with header `Idempotent-Replayed: true`.

## 4. Keyset / Cursor-Based Pagination

### Why Naive `OFFSET / LIMIT` Fails at Scale
1. **$O(N)$ Database Scans:** `SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;` requires the database engine to scan 100,020 index tuples and discard 100,000 before returning 20.
2. **Data Drift & Phantom Reads:** If rows are inserted or deleted while a client navigates pages:
   - Newly inserted rows shift existing rows downward, causing the client to see the same item twice on page 2.
   - Deleted rows shift existing rows upward, causing items to be skipped entirely.

### Keyset (Cursor) Pagination Mechanics
Instead of skipping records by count, seek directly after the last seen key using indexed order attributes:
```sql
SELECT id, customer_id, total, created_at
FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 21; -- Request limit + 1 to calculate has_more
```

### Parameter Contract
- `limit` (integer): Number of items per page (default: 20, max: 100).
- `starting_after` (string): Opaque cursor pointing to the last item of the previous page for forward traversal.
- `ending_before` (string): Opaque cursor pointing to the first item of the current page for backward traversal.

### Cursor Encoding
Cursors should be opaque to the client (typically base64-encoded JSON or signed tokens):
```
// Plain payload: {"id": "ord_9182", "created_at": 1726052000}
// Base64 cursor: eyJpZCI6Im9yZF85MTgyIiwiY3JlYXRlZF9hdCI6MTcyNjA1MjAwMH0=
```

### Standard Response Envelope
```json
{
  "data": [
    {
      "id": "ord_9182",
      "total": 149.50,
      "status": "completed",
      "created_at": "2026-09-11T09:15:00Z"
    }
  ],
  "pagination": {
    "limit": 20,
    "has_more": true,
    "next_cursor": "eyJpZCI6Im9yZF85MTgyIiwiY3JlYXRlZF9hdCI6MTcyNjA1MjAwMH0=",
    "prev_cursor": null
  }
}
```

## 5. Webhook Reliability & Delivery

Webhooks transmit event notifications to external client systems across the untrusted public internet. Delivery systems and consumer handlers must be resilient to failures and replay attacks.

### 1. Cryptographic Signature Verification (HMAC-SHA256)
Every outbound webhook **MUST** be cryptographically signed using a shared secret.

#### Headers:
```http
POST /webhook HTTP/1.1
Host: client.example.com
Content-Type: application/json
X-Signature: t=1726052400,v1=9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
X-Event-Id: evt_01J7K8Z3Q9W5P1A2M4N6B8C0D
```

#### Signing Algorithm:
```
signed_payload = "${timestamp}.${raw_json_body}"
signature = HMAC_SHA256(webhook_secret, signed_payload)
```

#### Consumer Verification Rules:
1. Extract timestamp `t` and signature `v1` from header.
2. Check timestamp freshness: Reject if `abs(current_time - t) > 300` (5 minutes tolerance) to prevent **replay attacks**.
3. Recompute HMAC-SHA256 signature using the shared secret and exact raw payload bytes.
4. Compare using constant-time string comparison (`timingSafeEqual` in Node.js, `hash_equals` in PHP) to prevent **timing attacks**.

### 2. Delivery Retries: Exponential Backoff with Full Jitter
Webhook endpoints frequently experience transient downtime, restarts, or deployment blips.
- Standard retry policy: **5 attempts** over approximately 8-12 hours.
- Retry interval formula (Exponential Backoff with Full Jitter):
  $$T_{retry} = \text{random}(0, \min(T_{max}, T_{base} \times 2^{\text{attempt}}))$$
- Example schedule:
  - Attempt 1: Immediate delivery
  - Attempt 2: 1 minute
  - Attempt 3: 5 minutes
  - Attempt 4: 30 minutes
  - Attempt 5: 2 hours
  - Attempt 6: 8 hours
- **Dead Letter Queue (DLQ):** Once all retries are exhausted, route the message to a DLQ and mark the webhook subscription endpoint as degraded or disabled.

### 3. Consumer Idempotency Protocol
- Webhook delivery guarantees **at-least-once delivery**, never exactly-once.
- Consumers **MUST** make event processing idempotent using an `event_id` tracking table:

```sql
CREATE TABLE processed_webhook_events (
  event_id VARCHAR(64) PRIMARY KEY,
  processed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

- **Consumer Processing Pattern:**
  1. Receive HTTP request.
  2. Verify HMAC signature and timestamp.
  3. Return HTTP `200 OK` or `202 Accepted` immediately (within 1 second).
  4. Dispatch event payload to an asynchronous background worker queue.
  5. Inside worker: Check `processed_webhook_events`. If `event_id` exists, discard safely. If not, process business logic inside a transaction and insert `event_id`.
